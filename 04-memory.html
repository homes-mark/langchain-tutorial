04 记忆（Memory）

阶段一 · 入门 难度：入门 前置：02 链、03 提示模板

学习目标

  • 理解为什么模型「无状态」需要记忆
  • 掌握缓冲、窗口、摘要三种记忆策略
  • 会管理历史消息与持久化

前置知识

  • 消息角色与 MessagesPlaceholder
  • 链式编排

4.1 模型是无状态的

LLM 本身不记得上次对话。每次 invoke 都是独立请求。所谓「记忆」，本质是把历史消息重新塞进下一次请求的上下文。因此记忆 = 历史消息的管理策略。

# 两次独立调用，模型并不知道前一次说了什么
model.invoke("我叫小明")
model.invoke("我叫什么？")   # 模型无法回答

4.2 缓冲记忆（最直观）

最简单的方式：手动维护一个消息列表，每次把新消息追加进去，全部一起发送。LangChain 1.x 中，推荐用 InMemoryChatMessageHistory + RunnableWithMessageHistory：

from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是友善的助手。"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])
chain = prompt | model

# 会话历史存储（按 session_id 区分不同用户/会话）
store = {}

def get_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

with_history = RunnableWithMessageHistory(
    chain,
    get_history,
    input_messages_key="input",     # 输入中哪个键是用户消息
    history_messages_key="history", # 历史注入到哪个占位符
)

# 第一轮
r1 = with_history.invoke({"input": "我叫小明"}, config={"configurable": {"session_id": "u1"}})
print(r1.content)

# 第二轮：模型记得名字
r2 = with_history.invoke({"input": "我叫什么？"}, config={"configurable": {"session_id": "u1"}})
print(r2.content)   # 小明
你好，小明！很高兴认识你。
你叫小明。
💡 session_id 的作用 configurable.session_id 是区分不同会话的「钥匙」。不同用户、不同对话用不同 id，历史就互不串扰。这是生产环境中多用户隔离的关键。

4.3 窗口记忆（控制长度）

缓冲记忆的问题：对话越长，token 越多，最终超出上下文窗口，且成本线性上升。窗口记忆只保留最近 N 轮：

from langchain_core.messages import trim_messages

# 在链中插入裁剪步骤，只保留最近 4 条消息
from langchain_core.runnables import RunnableLambda

def trim_history(messages: list) -> list:
    return messages[-4:]   # 只保留最近 4 条

# 提示：system + 裁剪后的历史 + 用户输入
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是友善的助手。"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])

更推荐用 LangChain 提供的 trim_messages，它支持按 token 数裁剪，而非简单按条数：

from langchain_core.messages import trim_messages

trimmer = trim_messages(
    max_tokens=500,           # 按 token 上限裁剪
    strategy="last",          # 保留最后的
    token_counter=model,      # 用模型的 tokenizer 计数
    include_system=True,      # 始终保留 system 消息
)

4.4 摘要记忆（压缩上下文）

窗口记忆会「遗忘」早期信息。摘要记忆用模型把历史对话压缩成一段摘要，既保留关键信息又控制长度。这是长期对话的常用方案：

from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

def summarize(history: list) -> str:
    """把对话历史压缩成摘要"""
    conv = "\n".join(f"{'用户' if isinstance(m, HumanMessage) else '助手'}: {m.content}" for m in history)
    summary_prompt = ChatPromptTemplate.from_template(
        "请把下面的对话总结为一段不超过 100 字的摘要，保留关键事实（如人名、偏好、任务）：\n{conv}"
    )
    return (summary_prompt | model).invoke({"conv": conv}).content

# 在每轮开始时，将摘要作为 system 的一部分
summary = summarize(history)
final_prompt = ChatPromptTemplate.from_messages([
    ("system", "你是友善的助手。对话历史摘要：{summary}"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])
⚠️ 常见误区：三种策略的取舍
策略优点缺点
缓冲完整、无损token 无限增长
窗口恒定开销丢失早期信息
摘要压缩保留要点有损、需额外一次模型调用
实际生产常组合使用：近期 N 轮保留原文 + 更早的用摘要，兼顾细节与长度。

4.5 持久化（跨重启保存）

InMemoryChatMessageHistory 重启即丢。生产环境需持久化到数据库或 Redis。核心是替换 get_history 的实现：

# 伪代码：接入 Redis 持久化
import redis, json

r = redis.Redis(host="localhost", port=6379)

def get_history(session_id: str):
    # 从 Redis 读取，返回实现了 BaseChatMessageHistory 的对象
    # 实际项目可用 langchain 社区的 RedisChatMessageHistory
    from langchain_community.chat_message_histories import RedisChatMessageHistory
    return RedisChatMessageHistory(session_id=session_id, redis_client=r)
✅ 最佳实践：安全与隐私 对话历史可能含敏感信息（个人信息、业务机密）。持久化时务必：加密存储、设置过期时间（TTL）、遵守数据合规（如 GDPR/个保法），并为用户提供删除会话的入口。

4.8 组合记忆完整实现

生产中最实用的是「摘要 + 窗口」组合：早期对话压成摘要，近期保留原文。下面给出完整可运行实现：

from langchain_core.messages import HumanMessage, AIMessage, trim_messages
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 摘要提示
summary_prompt = ChatPromptTemplate.from_template(
    "将以下对话浓缩为 50 字内的要点（保留人名、偏好、任务等关键事实）：\n{history}"
)

def build_summary(history_text: str) -> str:
    return (summary_prompt | model).invoke({"history": history_text}).content

# 组装：system 含摘要 + 近期原文
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是贴心助手。以下是此前对话的要点摘要：\n{summary}"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])
chain = prompt | model

# 会话状态：保存摘要 + 近期消息
store = {}

class SessionState:
    def __init__(self):
        self.summary = ""
        self.recent = []   # 只保留最近 N 条

def get_history(session_id: str):
    if session_id not in store:
        store[session_id] = SessionState()
    return store[session_id]

def chat(session_id: str, user_input: str) -> str:
    state = get_history(session_id)
    resp = chain.invoke({
        "summary": state.summary,
        "history": state.recent,
        "input": user_input,
    })
    # 更新：追加新消息，若过长则压缩为摘要
    state.recent.append(HumanMessage(user_input))
    state.recent.append(AIMessage(resp.content))
    if len(state.recent) > 4:   # 超过 2 轮就压缩
        old_text = "\n".join(m.content for m in state.recent[:-2])
        state.summary = build_summary(old_text)
        state.recent = state.recent[-2:]
    return resp.content
✅ 最佳实践：摘要时机 不必每轮都重新摘要（浪费一次模型调用）。可以设定阈值——当历史超过 N 条或 token 超限时才触发摘要，把摘要计算摊薄到多轮中，兼顾效果与成本。

4.9 动手练习

练习 4.1：多会话隔离 （入门）

用 RunnableWithMessageHistory 创建两个不同 session_id，分别告诉模型不同名字，验证两者历史互不干扰。

验证方法：session A 问「我叫什么」返回 A 的名字，session B 返回 B 的名字，互不串扰。
练习 4.2：实现窗口裁剪 （进阶）

在 4.1 的基础上，让历史只保留最近 2 轮，模拟长对话，观察早期信息被遗忘的现象。

验证方法：连续对话多轮后，追问第 1 轮的信息，模型回答「不知道」，验证窗口裁剪生效。
练习 4.3：摘要记忆 （进阶）

实现一个「摘要 + 近期原文」的组合记忆：早期对话压缩成摘要，最近 2 轮保留原文，观察模型既能记住早期关键信息又能应对细节追问。

验证方法：长对话后，模型仍能回答早期定下的「偏好/任务」，且 token 消耗明显低于全量缓冲。
练习 4.4：用 trim_messages 按 token 裁剪 （进阶）

用 trim_messages（而非手写切片）按 token 上限裁剪历史，设置 max_tokens=300，观察裁剪边界。

验证方法：打印裁剪前后的消息数，确认 system 消息始终保留、总 token 不超过阈值。
