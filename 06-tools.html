06 工具调用（Tool Calling）

阶段二 · 进阶 难度：进阶 前置：02 链

学习目标

  • 理解工具调用的机制与作用
  • 用 @tool 定义结构化工具
  • 掌握模型如何返回工具调用请求

前置知识

  • Python 类型注解与 Pydantic
  • LCEL 链

6.1 为什么需要工具

模型只会「生成文本」，它本身不能查实时数据、不能执行代码、不能访问数据库。工具调用（Tool Calling / Function Calling）让模型能够：决定要调用哪个函数 → 生成结构化参数 → 由我们的代码真正执行 → 把结果返回给模型。

这是构建 Agent 的核心能力——模型从「只会说」升级为「会说也会做」。

6.2 用 @tool 定义工具

@tool 装饰器把普通 Python 函数变成工具。关键在于类型注解和 docstring——它们会被自动转成工具的描述（schema），供模型理解「何时、如何调用」：

from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的当前天气。city 参数应为中文城市名，如"北京"。"""
    # 这里模拟返回，实际应调用天气 API
    weather_db = {"北京": "晴，25°C", "上海": "多云，28°C"}
    return weather_db.get(city, f"未找到{city}的天气数据")

@tool
def multiply(a: float, b: float) -> str:
    """计算两个数的乘积。a 和 b 为需要相乘的数值。"""
    return f"{a} × {b} = {a * b}"

# 查看工具的描述（模型就是靠这个理解工具）
print(get_weather.name)
print(get_weather.description)
print(get_weather.args)   # Pydantic 模型，定义了参数结构
get_weather
查询指定城市的当前天气。city 参数应为中文城市名，如"北京"。
{'city': {'title': 'City', 'type': 'string'}}
💡 docstring 决定成败 工具的 docstring 是模型判断「何时调用、参数填什么」的唯一依据。写清楚：工具用途、每个参数的含义、合法取值、返回内容。描述模糊 = 模型调用错误率高。

6.3 绑定工具到模型

用 bind_tools 把工具告诉模型。模型会返回 tool_calls 而不是普通文本：

from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
model_with_tools = model.bind_tools([get_weather, multiply])

resp = model_with_tools.invoke("北京今天天气怎么样？")
print(resp.tool_calls)
[{'name': 'get_weather',
  'args': {'city': '北京'},
  'id': 'call_abc123',
  'type': 'tool_call'}]

模型没有真正执行，只是生成了「我想调用 get_weather(city='北京')」的请求。需要我们自己执行并把结果返回：

from langchain_core.messages import HumanMessage, ToolMessage

# 1. 模型决定调用工具
resp = model_with_tools.invoke([HumanMessage("北京今天天气怎么样？")])

# 2. 手动执行工具
for tc in resp.tool_calls:
    result = get_weather.invoke(tc["args"])   # 真正执行
    # 3. 把结果包装成 ToolMessage 返回给模型
    tool_msg = ToolMessage(content=result, tool_call_id=tc["id"])
    resp = model_with_tools.invoke([HumanMessage("北京今天天气怎么样？"), resp, tool_msg])

print(resp.content)
北京今天天气晴，气温 25°C。

6.4 结构化参数（Pydantic）

复杂参数用 Pydantic 模型定义，让模型输出严格遵循结构：

from pydantic import BaseModel, Field

class SearchArgs(BaseModel):
    """搜索参数"""
    query: str = Field(description="搜索关键词")
    limit: int = Field(default=5, description="返回结果数量", ge=1, le=20)

@tool(args_schema=SearchArgs)
def search_docs(query: str, limit: int = 5) -> str:
    """在内部知识库中搜索文档。query 为关键词，limit 为返回条数。"""
    return f"搜索「{query}」的前 {limit} 条结果..."

6.5 误区与最佳实践

❌ 误区：工具无副作用假设 工具可能执行不可逆操作（删除数据、发送邮件、扣款）。不要让模型直接调用危险工具而不加任何保护。应：区分「读」与「写」工具，写操作加人工确认（Human-in-the-loop）、权限校验、幂等设计。
❌ 误区：信任模型的参数 模型生成的参数可能含错误或恶意内容（如 SQL 注入）。工具内部必须校验参数（类型、范围、白名单），绝不能把模型参数直接拼进 SQL/命令。
✅ 最佳实践
  • 工具保持单一职责，一个工具只做一件事。
  • 用 Pydantic 定义严格 schema，而非自由字符串。
  • 工具要有超时、重试、错误处理，返回清晰错误信息给模型。
  • 为工具写单元测试，隔离外部依赖（mock 掉 API 调用）。

6.8 封装自动工具循环

手动循环繁琐且易错。可以封装一个通用函数，自动处理「调用→执行→回传」直到模型给出最终答案：

from langchain_core.messages import HumanMessage, ToolMessage, AIMessage

def run_tool_loop(model, tools, user_input: str, max_steps: int = 5) -> str:
    """自动执行工具循环，直到模型返回最终答案"""
    messages = [HumanMessage(user_input)]
    tool_map = {t.name: t for t in tools}

    for _ in range(max_steps):
        resp = model.invoke(messages)

        # 没有工具调用 → 已是最终答案
        if not resp.tool_calls:
            return resp.content

        # 有工具调用 → 逐个执行并回传
        messages.append(resp)
        for tc in resp.tool_calls:
            tool = tool_map[tc["name"]]
            result = tool.invoke(tc["args"])
            messages.append(ToolMessage(content=result, tool_call_id=tc["id"]))

    # 达到最大步数仍未收敛
    return "（已达到最大工具调用次数，未能完成任务）"

answer = run_tool_loop(model_with_tools, [get_weather, multiply], "北京天气如何？")
print(answer)
💡 这就是 Agent 的雏形 这个 run_tool_loop 函数本质上就是第 07 章 create_agent 内部做的事——循环调用模型、执行工具、回传结果，直到收敛。理解它，你就理解了 Agent 的全部底层逻辑。
